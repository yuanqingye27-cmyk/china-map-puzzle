# 架构与可移植性评估（2026-09-17）

> 这份文档回答四个问题：
> ① 「秒级接完全国地图」到底是怎么做到的、前序工作提供了什么；
> ② 网页背后的运行逻辑与框架；
> ③ 想移植到 iOS / Android / 桌面端，哪些能直接搬、哪些必须重写；
> ④ 实测发现的 bug、冗余与不合理之处。
>
> 所有数字都是**实测值**（命令与结果附在对应位置），不是估计。

## 一、「秒级」的准确含义（别被这个说法误导）

**准确说法**：`batch-add-maps.js` **生成一个省的全部地级地图包**是秒级
（实测：广东 19 个市 **1.55 s**、面积补全 **0.097 s**）。
但**它快不是因为脚本神奇，而是因为三件前置工作早就完成了**。

### 生成流程（一张地图包的三步）

```
① 拉取该省的 _full.json（天地图官方服务中心，一次 HTTP）
   └─ 例如 https://.../bound/440000_full.json → 19 个市的边界
② 每个市再拉一次它自己的 _full.json → 得到它的区县边界
③ 纯计算：投影 → 量 bbox → 生成三个文件（.js / .geo.js / .data.js）
```

**网络是唯一慢的部分**（19 个市 ≈ 1.5 s）。第 ③ 步是纯计算，几十毫秒。

### 为什么能这么快：三件前置工作

| 前置工作 | 谁做的 | 省掉了什么 |
| --- | --- | --- |
| **1. 官方数据源的适配层** | 前序工作（SOP 5.12） | 天地图返回的是**二进制打包**而非 GeoJSON，要解码才能用。这层已封装成 `tools/lib/tianditu-portal.js`，调用方只看到"给我 adcode 的边界" |
| **2. slug 表（现 492 条）** | 本轮补全 | 地图包的目录名要拼音（`shenzhen`），拼音**推不出来**。原表只有四川 21 条，其余会兜底成 `map-440300` 这种不可读名字 |
| **3. 批量脚本 + 目录规则** | 前序工作（SOP 5.11） | 「父级没接入会自动补祖先」+「目录名 = 父目录 + id」这一条递归规则，使加一张地图是**纯追加**操作，不用回头改别人 |

**关键：这套结构让"加一个省"从"写代码"变成"跑一条命令"。** 我本轮做的事里，
真正花时间的是**发现和修复那三个隐蔽 bug**（见第四节），不是生成地图。

### 实测命令与结果

```bash
$ time node tools/batch-add-maps.js --parent=440000     # 广东 19 个市（已接入，走重跑）
real  0m1.551s
子级总数：19　新建：0　已存在：19　失败：0

$ time node tools/area-from-geo.js --parent=440000 --write
real  0m0.097s
```

## 二、运行逻辑与框架

### 2.1 分层（这是本项目的核心设计）

```
┌─ 宿主页面 ─────────────────────────────────────────┐
│ index.html + css/style.css                         │
│   只提供 DOM 骨架与样式，不含游戏逻辑               │
└────────────────────────────────────────────────────┘
            │ 引入 5 个脚本
            ▼
┌─ 启动器 js/game.js（244 行）────────────────────────┐
│ 地图选择器 / 面包屑 / 主题与音效开关                 │
│ 决定"何时 init() 引擎"，自己不碰拼图逻辑             │
└────────────────────────────────────────────────────┘
            │
            ▼
┌─ 引擎 js/engine.js（1554 行）──────────────────────┐
│ 拼图玩法全部在这里：拖拽 / 落点判定 / 关卡 / 进度 /  │
│ 信息卡 / 计时 / 音效 / 主题 / 结算                   │
│ 对外只暴露两个入口：{ start, getState }              │
└────────────────────────────────────────────────────┘
            │ 吃两样输入
            ├────────────────┬──────────────────────┐
            ▼                ▼                      ▼
┌─ js/geomap.js ─┐  ┌─ 地图包（数据）──────────┐
│ 投影 + 几何构建 │  │ <id>.geo.js  边界（产物）│
│ 181 行，纯计算  │  │ <id>.data.js 资料+关卡   │
│ **零 DOM 依赖** │  │ <id>.js      配色/存储键 │
└────────────────┘  └──────────────────────────┘
            ▲
            │ 由 loader 按需注入
┌─ js/maps/loader.js（151 行）───────────────────────┐
│ 按 id 注入那三个文件；路径由 dir+id 现算            │
│ 首屏只载 registry.js，**不载任何地图数据**          │
└────────────────────────────────────────────────────┘
```

### 2.2 一次加载的完整数据流

```
① 首屏：index.html 引入 registry.js + loader.js + geomap + engine + game
    registry.js 只有元信息（id/name/parent/adcode/children/dir），77 KB
    **不含任何地图边界** —— 这是"地图再多首屏也不变重"的关键
② 用户选地图（或 URL ?map=shenzhen）
③ loader 由 registry 条目推出三个脚本路径，依次注入：
      shenzhen.geo.js   → 边界（最多 100+ KB）
      shenzhen.data.js  → 资料卡与关卡
      shenzhen.js       → 把上面两份组装成 CONFIG，登记到 MAP_PACKAGES
④ game.js 取到包，调 engine.start()
⑤ 引擎用 geomap 算 path/bbox/质心，渲染凹槽与碎片
⑥ 拖拽落点判定（engine.js resolveDrop）：
      先 isPointInFill 精确命中多边形
      再退回"离凹槽质心够近"（小形状/手抖兜底）
⑦ 进度写 localStorage，key = <id>-map-puzzle（每张地图互不干扰）
```

### 2.3 实测体积（重要：决定可移植策略）

| 项 | 未压缩 | gzip |
| --- | --- | --- |
| 首屏合计（html+css+5 脚本） | **226 KB** | **60 KB** |
| 其中 registry.js | 77 KB | 9.7 KB |
| 单张地图按需加载（例：深圳） | ~24 KB | — |
| 全部地图（363 张） | 20 MB | — |

> **registry.js 已占首屏的 34%**。它是唯一随地图数线性增长的首屏文件
> （本轮已去掉可推导字段，-32%；但要接几千个县级地图时它还会继续涨，
> 见第四节的待办）。

## 三、可移植性评估：哪些能搬，哪些必须重写

我把代码按「与平台的耦合程度」分成三类，这是移植工作量的真实分布：

### A 类 · 可以直接搬（几乎零改动）

| 模块 | 行数 | 为什么能搬 |
| --- | --- | --- |
| `js/geomap.js` | 181 | **纯计算，零 DOM**（实测 grep `document\|window\|localStorage` 命中 0）。
唯一的平台耦合是文件末尾 `global.GeoMap = {...}` 这一行导出 |
| 全部地图包（`js/maps/**`） | 20 MB | **纯数据**。`.geo.js` / `.data.js` / `.js` 都是"给一套假 window 就能求值的 IIFE"，
不含任何平台 API |
| `tools/lib/geo-area.js` | 132 | 球面面积纯计算。**移动端也需要它**（面积就是用它算的） |
| `tools/lib/facts-source.js` 的抽取规则 | — | 纯正则与字符串处理 |

### B 类 · 需要改造（有边界，但量不小）

| 模块 | 耦合点 | 实测 |
| --- | --- | --- |
| `js/engine.js` | **62 处 `document.`** | 集中在少数几处：`cacheDom()`（约 20 个元素引用）、
`buildMap/createSlot/createPiece`（SVG 创建）、`onPointerDown/Move/Up`（拖拽）、
主题切换（切 CSS 类）、音效（Web Audio）、存档（localStorage） |
| `js/game.js` | 16 处 DOM | 选择器/面包屑 UI |

### C 类 · 平台专属，本来就要重写

CSS 动画（47.8 KB 里的动画与视觉）、index.html 骨架、`tools/` 全部脚本（构建期工具，不随 App 发布）。

### 移植路线的三条现实选项

| 路线 | 工作量 | 体验 | 适合 |
| --- | --- | --- | --- |
| **① WebView 壳**（Capacitor / WKWebView） | **最小**（几乎零改动） | 与网页一致；手势/动画在原生 WebView 上够用 | 想最快上架 iOS/Android |
| **② 提取纯逻辑 + 原生 UI** | **大**（要重写 engine 的渲染与输入层，约 900 行） | 最好（原生手势、硬件加速） | 想长期做多端产品 |
| **③ 复用 geomap + 数据，游戏逻辑重写** | 中 | 好 | 只要"拼图"这一件事搬到别的技术栈（如 Flutter/Unity） |

### 为路线 ②/③ 铺路：engine.js 里真正该被抽出来的三块

按"是否含平台 API"分，**逻辑其实比想象中集中**：

1. **关卡状态机**（纯逻辑，可搬）
   `currentLevel / startLevel / tryPlace / commitPlace / finishLevel / snapshotState`
   —— 它操作的是 `placed:Set / tries / hints / solved / unlocked`，
   **唯一与 DOM 的接触是"拿到落点后更新元素"**。把这一步改成回调即可。
2. **落点判定**（纯逻辑，可搬）
   `resolveDrop()` 的逻辑只依赖"点在哪个多边形内"，与 SVG 无关 ——
   换成任意平台的多边形命中测试都能复用。
3. **几何→屏幕坐标**（纯逻辑，可搬）
   `screenToMap / bboxToScreen / computeLevelViewBox / animateViewBox` ——
   本质是"viewBox 变换"，任何渲染层都有等价概念。

> **建议的渐进路线（低风险）**：
> 先在 engine.js 里把这三块**显式分层**（哪怕暂时还在同一个文件里）：
> 状态机只依赖一个注入的 `renderer` 接口（`drawSlots / updatePiece / showInfo / toast`），
> 而不直接调 `document.*`。这样以后接任何平台只需实现这个 renderer，
> 而不是重读 1554 行。

## 四、实测发现的 bug、冗余与不合理

### 4.1 已修（本轮）

| 问题 | 性质 | 影响 |
| --- | --- | --- |
| 省级 geo 混入"地图自己"的 feature | **真 bug** | 6 张省级地图拖拽判定全错乱 |
| slug 撞名（吉林市/海南州/河北区） | **真 bug（静默）** | 地图没建成，报告只说"跳过 1" |
| 无下级的行政区被单独建地图 | **真 bug（会崩）** | 123 张空地图 → 引擎抛 `adcodes` 错误 |
| registry 存可推导字段 | 冗余 | 首屏体积 +32% |

### 4.2 新发现的冗余（本次实测，尚未修）

**① `level.color` 是死字段**

```js
// <id>.data.js 的关卡对象
{ id, name, short, color: '#6b39d0', blurb, adcodes }
```

- 生成端：`tools/add-map.js` 写入 `hslToHex(hueFor(adcode, i))`
- 消费端：**全项目没有任何地方读 `level.color`**（实测 `grep -rn '\.color' js/` 无命中）
- 引擎实际用的是 `level.hue → PALETTE.hueByLevel[level.id] → fallbackHue` 这条链

→ **每个关卡白存一个 hex 字符串**，且它给了人"改这个能换颜色"的错觉。
建议：要么删掉字段，要么让引擎真的用它（二选一，别留着）。

**② 「关卡内配色」有两套机制并存**

- 路径 A：`hueFor()` 在**生成期**把色相烘进 `hueByLevel`
- 路径 B：引擎 `colorOf()` 还有 `level.hue → hueByLevel → fallbackHue` 三级兜底

**这两套是有意分层**（生成期给默认、运行期可覆盖），**不是 bug** ——
我一开始误判成"三重冗余"，查证后纠正。
但**文档没写清楚"哪一层是主、哪一层是兜底"**，容易让人改错地方。
建议在 `.data.js` 与 `engine.js` 各加一行注释说明优先级。

**③ `PROVINCE_SLUGS` 在 add-map.js 里有第二份引用**

```js
// tools/add-map.js:58
const PROVINCE_SLUGS = slugs.PROVINCE_SLUGS;   // 别名，不是副本（无实际问题）
```

本身无害（指向同一个对象），但**留下"这里可以各改各的"的歧义**。建议直接用 `slugs.PROVINCE_SLUGS`。

### 4.3 结构性问题（架构层面，需要你决策）

**① registry.js 是"首屏单点"**

现在 77 KB（gzip 9.7 KB）。看起来还行，但它**随地图数线性增长**：
若将来把 2701 个县级也各建成地图包，registry 会到 **约 600 KB**。
届时的解法（按优先级）：
1. **按省拆分 registry**：首屏只载"当前地图的祖先链 + 兄弟"（几 KB）
2. 首屏只载"省级清单"，进省后再载该省的地级清单
3. 保持现状（只在真要接几千张地图时才需要处理）

**② 引擎的 DOM 耦合没有边界（可移植性的最大障碍）**

见第三节。**这不是 bug，但它是"以后想移植"的主要成本**。
按上面建议做"状态机 / 渲染器分离"即可显著降低。

**③ `js/maps/<省>/<市>.data.js` 与 `<省>.data.js` 的职责重叠**

- `<省>.data.js` 装的是**该省的各地级市**资料（如四川省的 21 个市）
- `<市>.data.js` 装的是**该市的各区县**资料

两者字段结构相同，但"哪一级的资料放在哪个文件"只靠约定。
**不过这个约定已经被测试保护住了**（我一开始以为没有，查证后纠正）：
`tools/test-maps.js` 对**每一张地图**都断言

```
<slug> 关卡覆盖全部行政区     # 关卡里的 adcode 必须恰好覆盖自己 geo 里的行政区
<slug> 每个行政区都有资料卡   # 每个行政区都要有资料条目
```

实测 363 个地图包零违规。所以"资料放错文件"会被立刻逮住 ——
**这是本项目既有设计里比较好的一点，评估时不要重复造这条断言**。

### 4.4 已确认"不是问题"的（避免以后重复怀疑）

| 怀疑 | 结论 |
| --- | --- |
| `hueFor` / `hueByLevel` 是冗余 | **不是**：生成期默认 + 运行期覆盖，有意分层 |
| 归档里有 131 MB 缓存拖慢项目 | **不是**：`.cache/` 与 `out/` 已 gitignore，不入库 |
| `soften-placeholders.js` 是无引用死文件 | **不是**：它是 CLI 工具（按名字调用，不被 require），且刚用过 |
| `tianditu-check.js` 是死文件 | **不是死代码，是休眠**：需 API Key 的旧路线，文档已标注 |

| 套件 | 项数 | 覆盖 |

| 防编造守门人自测 | 20 | 7 种输入，要求"该拦的必须拦住" |

**总 10961 项**。这套测试是"敢重构"的底气 —— 尤其 `engine-test.html`
用虚构地图测引擎，**改引擎时不必担心地图数据**。

`test-maps.js` 里**逐张地图**跑的断言（每张都过一遍，这是它 1822 项的来源）：

| 断言 | 抓的是哪类错 |
| --- | --- |
| `<slug> 三件套齐全` | 缺文件 |

> 本次评估我就差点把一个**已存在**的不变量当成"缺失"提出来（见 4.3 ③）。

## 五、给"以后编辑修改"的建议（按优先级）

1. **改引擎前先看 `engine-test.html`**：它用虚构 tiny-city，
   能在不看任何真实地图的前提下验证引擎行为。这是最便宜的回归手段。
2. **改地图生成逻辑后必须重建 registry**：
   `node tools/build-registry.js`。本轮就踩过"改了配置但登记册是旧的"，
   被冒烟测试的"标题栏文案跟着地图走"逮住。
3. **不要手改 `js/maps/registry.js`**：它是生成产物，改动会被覆盖。
4. **新增地图只走两条命令**：
   `batch-add-maps.js`（生成）→ `area-from-geo.js`（面积），都不用手写文件。
5. **要移植就先做"状态机 / 渲染器分离"**，别直接开始写原生 UI。
6. **排查单张地图别跑全量**：`--only-maps=<ids> --only-suite=smoke`。
